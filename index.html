Criterios de Evaluación y Diseño

Principios técnicos que sustentan y validan cada una de las tres soluciones propuestas:

1. Problema y Usuarios Reales
Necesidad concreta y verificable en un sector productivo o social. Se resuelve un cuello de botella operativo real con valor medible para sus actores.
2. Arquitectura de Datos Especializada
Uso justificado de SQLite, Redis y/o MongoDB con una función técnica irremplazable: transaccionalidad local ACID, concurrencia in-memory atómica o flexibilidad documental.
3. Alcance MVP Acotado (2–3 Semanas)
Límites claros y estrictos de ejecución. Módulos esenciales funcionales y descarte deliberado de elementos secundarios para asegurar entrega con código abierto.
4. Validación Técnica y Proyección TFG
Evidencias cuantitativas medibles (concurrencia, latencia, resiliencia ante fallos) y base sólida para extender hacia Trabajo Final de Graduación con IA o IoT.
Enfoque Premisa de ingeniería: Soluciones de alto impacto con arquitectura especializada, alcance realizable y validación cuantitativa.

Propósito Central

PROPUESTA 1 · QLINE FUNDAMENTO & ARQUITECTURA

QLine · Propósito y Arquitectura de Datos

Lema de arquitectura: "MongoDB conserva lo que ocurrió. Redis controla lo que ocurre ahora."

El Problema y los Actores
Dolor Operativo: Salas de espera colapsadas, desorden en pasillos y riesgo crítico de que dos operadores en ventanillas distintas llamen al mismo turno simultáneamente.
  • Cliente / Paciente: Genera turno con QR y monitorea su posición en sala.
  • Operador de Ventanilla: Acciona "Llamar siguiente" atómicamente y atiende.
  • Supervisor: Supervisa en vivo tiempos de espera y audita cumplimiento de SLA.
Motores Justificados
• Redis (¿Qué ocurre ahora?): Cola activa con prioridades, llamadas atómicas (LPOP) anti-duplicados y TTL de 180s ante abandono.
• MongoDB (¿Qué ocurrió?): Colección inmutable turnos con marcas de tiempo (creado, llamado, finalizado) y reportes de SLA.
// db.turnos (Documento JSON) { "codigo": "A-015", "servicio": "Cajas", "prioridad": "preferencial", "estado": "atendido", "ventanilla": "V-02", "operador": "Carlos M.", "timestamps": { "creado": "09:12Z", "llamado": "09:18Z", "finalizado": "09:23Z" }, "metricas": { "espera_seg": 382, "atencion_seg": 323 } }
Resiliencia Estrategia de Caída: Si Redis se cae, MongoDB conserva todos los turnos pendientes; al reanudar, un daemon rehidrata la cola en Redis sin pérdida de datos.

PROPUESTA 02 · IMPACTO SOCIAL & ECONOMÍA CIRCULAR

NUTRIBRIDGE

Plataforma Comunitaria de Gestión de Donaciones y Banco de Alimentos
"SQLite captura en el acopio sin red. Redis prioriza por caducidad. MongoDB audita el impacto social."
Propósito Central
Rescatar alimentos perecederos donados por supermercados y distribuidores, despachándolos de emergencia a comedores y albergues mediante prioridad FEFO (First-Expired, First-Out) y soporte de captura offline en bodegas.
SQLITE: Acopio Local Offline REDIS: Despacho FEFO & TTL MONGODB: Trazabilidad & Impacto Social
PROPUESTA 2 · NUTRIBRIDGE FUNDAMENTO & ARQUITECTURA

NutriBridge · Propósito y Arquitectura de Datos

Lema de arquitectura: "SQLite captura en el acopio sin red. Redis prioriza por caducidad. MongoDB audita el impacto social."

El Problema y los Actores
Dolor Operativo: Toneladas de alimentos frescos (lácteos, verduras) se pierden por lentitud en contactar albergues antes de que caduquen, sumado a camionetas de recolección sin conexión.
  • Donante (Supermercados/Agro): Registra lotes por vencer y cantidad.
  • Voluntario / Camión de Acopio: Pesa y recibe cajas en SQLite local sin señal.
  • Comedor / Albergue: Acepta asignaciones relámpago antes de la caducidad.
Sinergia de 3 Motores
• SQLite (Edge): Buffer transaccional local en el camión sin internet.
• Redis (Tiempo Real): Cola FEFO ordenada por timestamp de vencimiento y alertas TTL.
• MongoDB (Historial): Fichas polimórficas de donantes y reportes de kg rescatados.
// db.donaciones (Documento JSON) { "_id": "DON-9042", "donante": "Supermercado Central", "alimento": { "categoria": "Lácteos", "kg": 120.5, "requiere_frio": true }, "vencimiento": { "fecha": "2026-10-08T18:00Z", "horas_utiles": 48 }, "estado": "despachado_fefo", "albergue_id": "Comedor San José", "trazabilidad": { "registrado_sqlite": "08:30Z", "sync_mongo": "09:15Z" } }
Sincronización Tolerancia a fallos: SQLite almacena transacciones en bodega; al detectar red sincroniza a MongoDB e inyecta en la cola FEFO de Redis.

PROPUESTA 3 · AGROLOGIC FUNDAMENTO & ARQUITECTURA

AgroLogic · Propósito y Arquitectura de Datos

Lema de arquitectura: "SQLite asegura la transacción en el surco. Redis acelera decisiones ejecutivas. MongoDB adapta la riqueza biológica del cultivo."

El Problema y los Actores
Dolor Operativo: Pérdida de certificaciones internacionales por anotaciones dispersas en WhatsApp y papel, violación de tiempos de carencia y parcelas sin cobertura 4G/5G.
  • Productor / Capataz: Registra labores diarias y dosis en el lote sin internet.
  • Ingeniero Agrónomo Inspector: Documenta plagas con fotos y fija carencias.
  • Gerente de Cooperativa: Supervisa consolidado y aprueba exportaciones.
Sinergia de 3 Motores
• SQLite (Edge): Tablas maestras fijas ACID en el móvil (Fincas, Lotes, Insumos).
• Redis (Tiempo Real): Caché de dashboards diarios y alertas de carencia.
• MongoDB (Cuaderno Flexible): Bitácoras heterogéneas multicultivo (fotos, plagas, audios).
// db.cuaderno_campo (Documento JSON) { "_id": "BIT-00431", "productor_id": 104, // Referencia SQLite "finca": "Hacienda Santa Elena", "parcela": "Lote 4 - Café", "evento": "fitosanitario", "detalles": { "plaga": "Broca del Café", "incidencia": "4.5%", "fotos": ["s3://..."], "insumo": "Beauveria bassiana", "dias_carencia": 15 }, "geo": { "lat": 10.0162, "lng": -84.1189 } }
Arquitectura Sincronización híbrida: SQLite valida estructura relacional fija en el surco; MongoDB absorbe la diversidad documental sin migraciones de esquema.
